# How the fork differs from upstream

How this fork, [kelno/claude-voice](https://github.com/kelno/claude-voice), differs from [claude-voice](https://github.com/roykollensvendsen/claude-voice) by Roy Kollen Svendsen and why, upstream's rules for a pull request, and how one is checked here. What could go back upstream is in `UPSTREAM-CANDIDATES.md`. Written to be picked up cold, by people and agents.

- "The owner" is kelno, who maintains this fork; "the relay" is the voice assistant in the Claude app that talks to the bridge for them; "agents" are the Claude sessions that do the work.
- The fork split from upstream at `21d1d96` (2026-10-29). It follows upstream by merging upstream's `main` into its own, so fork commits keep their hashes; the last merge took upstream's `4fe55dd` (2026-11-19). The history from before 2026-11-06, when the fork was once rebuilt on upstream with every commit replayed, is on the fork's branch `main-before-resync`, so older commits are named by their subject (find one with `git log --grep`), not their hash. Upstream moves fast; check what it has taken before offering anything.

## Upstream's rules

Upstream's own rules for a pull request: [`CONTRIBUTING.md`](https://github.com/roykollensvendsen/claude-voice/blob/main/CONTRIBUTING.md) and [`AGENTS.md`](https://github.com/roykollensvendsen/claude-voice/blob/main/AGENTS.md) (in the contribute worktree: `git show upstream/main:CONTRIBUTING.md`). The procedure below adds only what applies to the owner's PC and to what upstream's author has asked of our pull requests.

## How we check a pull request here

The full ratchet switches every rule off in turn, one test run per rule in `scripts/mutations/` (one file per rule, under the whole path of the file it switches off), and runs out of memory locally, so the mutation sweep is left to upstream's CI, which runs the full ratchet on every pull request. For each pull request:

1. The tests the change touches, `ruff check`, `ruff format --check` and `mypy src`; each new test seen failing at the `test:` commit. A row added or changed in `scripts/mutations/` is checked by `tests/test_rules_have_evidence.py`, which applies every row and checks the file still compiles (the runner replaces the whole matched line, so a replacement written as part of a line breaks the import). Whether the rule's own test goes red is only seen in a mutation run, so for a new row, apply it by hand and run that one test. On #109 (2026-11-10), a row cut off mid-expression went unnoticed until upstream's CI. A change that adds a copy of a line a row looks for can also make that rule's mutation miss (seen on `wait_for_session`).
2. Commit bodies wrapped at 72 characters: the author asked for it on #129 (2026-11-10), though their commit lint allows 100.
3. The session opens the draft itself, with `gh pr create --draft --repo roykollensvendsen/claude-voice`, signed in with the agents' GitHub account. If CI then reports a mutation that survived, fix it and push again.
4. This is done in the contribute session (`start_role`; see "Upstream features, and how they're set here") (owner).

### Upstream features, and how they're set here

All of upstream's code is in; what is on or off here (owner):

- Self-update (`update_changes`, `update_bridge`): on. It pulls the branch the bridge's clone follows, the fork's `main` on GitHub, never upstream, and only as a fast-forward; it refuses to start with local changes, and rolls back on failure. Upstream's changes come only by a resync. What an update brings is read from the commit messages, grouped by kind. On Windows it restarts the bridge by exit code 75 (see "Same tools, different behaviour").
- Contribute role (`start_role`): on. Its folder, a separate worktree of the fork on upstream's `main` and never the clone the bridge runs from, is set for this PC in `~/.config/claude-voice/config.toml` (`[paths] contribute`). Its first message sends it to "How we check a pull request here", which wins where upstream's brief differs. No rules live in machine-local files (owner).
- `check_dependencies`: on, as upstream has it.
- Chosen session (`get_active_session`, `set_active_session`) and `refresh_session_summary`: off (see the table above).
- Repository permission rules (`claude-voice permissions`), with the rules that ask first that upstream added on 2026-11-12 (a push to main, GitHub writes others read, device tools): in, upstream's table never applied here (owner): its rules cover only the Bash tool and forward-slash paths, and most sessions here open in a folder it doesn't write to: it writes only into the bridge's own clones named in its settings (here just the fork's clone, with no web or phone app clone and no plugin), while sessions here open in the folders above it. Not used here, and no table of the fork's own is planned for now (owner, 2026-11-17).
- The work page (`/api/v1/work`) and bringing a session's terminal to the front: in, as part of the companion API, unused here (owner): the page lives in the companion app, which isn't installed, and what waits on the owner is kept in the owner's own notes; the terminal part needs a Linux GNOME desktop, and on Windows a desk session can raise a window when asked.
- Companion app: off. Its API code is in, with upstream's waiting for the phone only while the owner is away from the laptop (`presence.py`, 2026-11-14 resync: away while the app is open, the screen is locked, after five minutes without keyboard or mouse, or for ten minutes after a voice call), inert here since no phone hook posts questions, and its reading of the desktop is GNOME's; it stays unused, since the owner doesn't use the companion app and doesn't plan to (owner, 2026-11-14), with upstream's closing of phone prompts no hook waits on any more and its phone hook fixes (only the questions the phone can answer, the box shown at once when the bridge refuses a wait), without its parts for sessions run inside the bridge; its event stream reads the watcher's events through `feed_news()`, a plain function, since `whats_new` is not a tool here.
