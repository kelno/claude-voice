# claude-voice

How a change is made here is in [CONTRIBUTING.md](CONTRIBUTING.md). What an
assistant must and must not do, installing the bridge or changing it, is in
[AGENTS.md](AGENTS.md). Both apply to every Claude session in this repository.

## The owner's fork

- This fork is an AI-managed repo: its owner, kelno, has their own AI agents maintain it for kelno's personal setup, under rules kept in kelno's private agent setup. Those rules don't apply to anyone else's agents; for anyone else, `CONTRIBUTING.md` is how a change is made.
- For kelno's agents working on the fork itself, the gates and the quality ratchet in `CONTRIBUTING.md` are slow checks, run as kelno's rules for AI-managed repos say, not before every push. On the fork's own `main`, that ratchet is `uv run python scripts/ratchet.py check --base origin/main --skip-mutation`: it compares the work with the fork's `main` as last pushed, measuring that in a copy (so it runs the suite twice), and the full mutation sweep is left to continuous integration. Nothing is recorded in `quality.json`: since upstream's ADR-CV-009 (2026-11-10), continuous integration keeps main's levels with each of its runs. A branch meant for a pull request to upstream is checked as `UPSTREAM.md` says ("How we check a pull request here").
- At the start of a session, run `git fetch upstream`. If `git rev-list --count $(git merge-base main upstream/main)..upstream/main` is above 0, tell the owner how many upstream commits the fork is behind and offer a resync, but never start one without the owner's OK. The last sync is the merge base of `main` and `upstream/main`, so it needs no marker of its own; a resync that rebuilds `main` on top of upstream moves it.
- Whenever a change makes the fork differ from upstream (a rename, a rework, keeping the fork's own version over upstream's, dropping or not taking an upstream change), record it in the same change, in this repository's `UPSTREAM.md`, under "Differences from upstream": what differs, why, and for a rename the old upstream name. Reasons get lost otherwise: the rename of `side_question` to `peek_session` was found again only from the owner's memory.
- A resync merges `upstream/main` into `main`: one merge commit, its conflicts resolved there once, against the fork's current code, and the fork's history never rewritten, so `main` is never force-pushed and upstream's commits keep their hashes. The merge commit only resolves the merge; work the merge calls for beyond that (reworking a fork feature to fit an upstream one, a renumbering, `UPSTREAM.md`) follows in commits of its own, each standing alone. A pull request to upstream is built on its own branch from upstream's `main` anyway, so the fork's history needn't be in its shape. Until 2026-11-08 a resync rebuilt `main` on upstream's and replayed the fork's commits on top; the owner chose the merge then, to resolve each conflicting area once rather than once per replayed commit.
- git's `rerere` is useful but optional: with `git config rerere.enabled true`, a conflict resolved once is resolved again by itself if the same merge is redone.
